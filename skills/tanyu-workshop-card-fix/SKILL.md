# 探域「话术未生成」→ 知识卡片闭环修复工作流

> ⛔⛔ **动笔前先过两条边界**（2026-10-26 起）
> - **尺码 / 选码 / 体重类 → 不进知识卡，一律改「尺码表技能」(SIZE_CHART)**。用户 2026-10-26 原话：「尺码表的这一类是需要在技能里面更新的，这个是规则」。细则见 §3 末。
> - 其余主题才走本技能的六步（判售前售后 → 边界 → 查重 → 写卡）。

## 0. 用户的标准工作流（原话）

> 首先去调优工坊找个店铺咨询回复中**待审核的话术未生成**，然后判断买家这个问题未回复属于**售前还是售后**；如果是售前知识，查看这个问题是否符合**人工与智能体回复边界**；符合并查看知识卡片是否有**相似的知识**，如果没有则找到这个商品的**知识卡片**，选择标题为**售前**的知识卡片，通过**生成话术**，**写入相对应的知识卡片**，从而使得这个话术未生成得以解决。

本技能就是把这句话变成可执行、可复跑的六步。

## 1. 六步总览

| 步 | 动作 | 产出 | 关键工具 |
|---|---|---|---|
| ① | 拉工坊「待审核 + 话术未生成」 | 待处理清单（按商品聚合） | `tools/workshop-pending.js` |
| ② | 判售前 / 售后 | 分流标记 | 词表（§3） |
| ③ | 过人工-AI 边界 | 红/黄/绿区 | 五维法（§4） |
| ④ | 查相似知识 | 「更新已有分段」还是「新增分段」 | 全库扫（§5） |
| ⑤ | 生成话术 | 1 分段正文（含文本框） | `customer-service-script-card` |
| ⑥ | 写进卡内新分段 | 线上落库 + 回读核验 | `tools/append-*-seg.js` 模式（§6） |

**只有绿区 + 无相似知识（或相似知识需补口径）才走到 ⑤⑥。** 红区一律不做卡。

**⛔ 例外：尺码类不走这六步** —— 直接转 `tanyu-size-chart`（见 §3 末）。给尺码补知识卡是无效动作。

## 2. ① 取数：什么叫「待审核 + 话术未生成」

- 接口：`POST https://agent.tanyuai.com/api/im/agent-trace/paginateV2`
- body：`{thirdShopId, pageIndex, pageSize, beginTime:"YYYY-MM-DD 00:00:00", endTime:"YYYY-MM-DD 23:59:59", type:["CONSULT_REPLY"]}`
- 前置：Playwright 先打开 `https://agent.tanyuai.com/v2/diagnostic-optimization/optimization-workshop` 带出登录态；`pageSize` 实测 500 可用。
- **⛔⛔ 筛选口径（2026-09-29 全面纠正，之前的写法是错的）**
  - ❌ **旧写法「`reviewStatus == 2 && content 为空` = 待审核未生成」完全错误，两个字段都用反了。**
  - ✅ **`reviewStatus=1` 才是「待审核」**，`reviewStatus=2` 是「已处理」。证据：UI 的「处理状态」下拉只有 `待审核 / 已处理` 两项，选中「待审核」下发的请求体是 `reviewStatus:1`；页面行内「处理状态」列的「待审核」也对应 `reviewStatus=1`（两条独立证据一致）。
  - ✅ **「话术未生成」是「未自动发送原因」里的一个值，服务端参数是 `noSendReasonList: [114]`**（114 = 话术未生成）。完整原因表见 §10。
  - ✅ **用户工作流的正确口径（= 页面上那个组合）**：
    ```
    { thirdShopId, beginTime, endTime,
      type: ['CONSULT_REPLY'],        // 话术类型 = 咨询回复
      reviewStatus: 1,                // 处理状态 = 待审核
      noSendReasonList: [114] }       // 未自动发送原因 = 话术未生成
    ```
    实测器械保健店 9/1–9/29 00:00 → **total = 395**，与页面显示的「共 395 条数据」完全一致。复现脚本 `tools/probe-repro395.js`。
  - ⛔ **`type:['CONSULT_REPLY']` 会把大部分未生成记录丢掉**：未生成的记录 84% 是 `CONSULT_PRODUCT`（商品咨询），只有 16% 是 `CONSULT_REPLY`。所以**先按 `noSendReasonList:[114]` 拉，再按需要过滤 type**，别反过来。
  - 三个口径互不相等，报数必须写明：`待审核`（reviewStatus=1）＞ `话术未生成`（noSendReasonList=[114]）＞ `待审核 ∩ 话术未生成`。器械保健店（近30天）：17,302 / 3,825 / 3,629。
  - `content` 空判断要兼容数组：`!(Array.isArray(c) ? c.filter(Boolean).length : String(c||'').trim())`。**「话术未生成」的记录 `content` 恒为空**，所以它才是真正意义上的「未生成」，不必再自己判空。
- **服务端可用筛选参数（逐个实测有效）**
  | 页面控件 | 参数 | 取值 |
  |---|---|---|
  | 处理状态 | `reviewStatus` | **数字** 1=待审核 / 2=已处理（传数组 `[2]` 报 `code:0`） |
  | 未自动发送原因 | `noSendReasonList` | **数组**，如 `[114]` |
  | 发送状态 | `sendType` | **数组**，`[0]`未发送 / `[1]`自动发送 / `[2]`侧边栏点击发送 / `[3]`编辑后发送 |
  | 话术类型 | `type` | **数组**，`["CONSULT_REPLY"]`咨询回复 / `CONSULT_PRODUCT`商品咨询 |
  | 标记状态 | `ifLabel` | 0=未标记 / 1=已标记 |
  | 时间 | `beginTime`/`endTime` | `YYYY-MM-DD HH:mm:ss` |
  传错字段名会被**静默忽略**（返回全量），所以每个字段都要先用总量验证有效性。
- **UI 对不上的排查顺序（2026-09-29 实测）**：
  1. 工坊页面默认窗口是**近 30 天**（打开时下发 `beginTime=今天-30`、无 type、无 reviewStatus），默认店铺是**上次选的那家**。
  2. 页面底部「共 N 条数据」= **选中筛选后的 total**；不选任何筛选就是全量。别把它当成待审核数。
  3. 还差 → **按用户截图里的筛选条件逐项抄成请求体**，用 `probe-repro395.js` 这类脚本复现到数值完全一致为止。**不要凭字段名猜语义**——本次就是猜 `reviewStatus=2` 才错了。
  4. 最稳的做法：`tools/probe-ui-pick.js` / `probe-ui-status.js` 用有头浏览器**真的去点一遍筛选**，从抓包拿请求体。

**找「该写哪张卡」的匹配规则**
- 只在该分组**已绑定**的卡里挑（`includeCondition.productGroupId` 含该组），先排除标题带「售后」的，再取标题带「售前」的。
- **卡标题常写成「膝部固定器（弧形护膝绑带P款）-售前（PDD）」——分组名在括号里**，所以归一化时只能去掉括号字符本身，**不能删括号内容**（踩过：删了就会把本品卡误判成通用卡）。
- 本品卡 vs 通用卡的判定：归一化后卡标题含完整分组名 → 本品卡；只含前 8 字主干 → 也算（兜住「AY-护膝艾草绑带（长款+短款）」↔「…护膝艾草绑带款」这类写法差）；都不含 → 通用/族卡。

## 3. ② 售前 / 售后 分流

判定要**两路交叉**，不能只看问题字面：

1. **语义**（主要）：交易前问信息＝售前；交易后问处置＝售后。
   - 售前：尺码 / 材质 / 规格 / 功效 / 哪款 / 区别 / 怎么选 / 有没有 / 能不能 / 适不适合 / 价格与优惠
   - 售后：已经收到 / 退了 / 换货 / 补发 / 少发漏发 / 破损 / 发票 / 物流 / 催发货 / 差价 / 评价 / 质保理赔
2. **卡片侧比对**：该商品分组下的卡通常按 `XX-售前`、`XX-售后` 成对命名（实测如「弧形护膝经典P款 -售前」与「弧形护膝经典P款-售后」）。**这条记录的问题语义和哪张卡的既有分段最像，就归哪边。**

> 售后走售后卡；若该商品**没有对应售后卡**，不要硬塞进售前卡 —— 记进"待建售后卡"清单交给用户。

### ⭐⭐ 订单状态维度（10-10 用户立，必须与售前/售后分流同步判）

判"售前/售中/售后"要**看会话订单状态**，不能只看语义；同时**查卡的 `orderStatus`**，否则会出现"知识明明有、话术却生成不出来"。

**探域阶段映射（UI 勾选项 → 接口值，用户 10-10 确认）**：

| 阶段 | 覆盖状态 | 接口值 |
|---|---|---|
| 售前 | 未下单、待付款、待成团、订单取消 | `PRE_SALE` |
| 售中 | 待发货 | `SALE` |
| 售后 | 已发货、交易成功、交易关闭、部分发货 | `AFTER_SALE` |

- **卡的 `orderStatus` 语义**：**空 / `[]` ＝ 不限阶段（覆盖全部）**；含 `AFTER_SALE` 才覆盖售后；非空且不含 `AFTER_SALE` ＝ **售后盲区**。
- ⛔ **铁律：没绑售后卡 ⇒ 售后话术必空**（写什么知识都召不回）。查覆盖**必须同步看 `orderStatus` 和 `ifOpen`**。
- ⭐ **实测（全库 939 张，10-10）**：**售后盲区 630 张（67.1%）**；标题含「售前」的 463 张里 **424 张是售后盲区**；185 个商品分组中 **45 组无任何含售后的卡**（该组商品售后必空）。脚本 `analyze-orderstatus-cards.py`。
- ⭐ **一些简单售后也可以做卡**（用户 10-10 定）：配件/赠品是否单卖、清洗保养、佩戴方法、质保/保修期、发票、使用注意 等**非红区售后**可做卡，卡 `orderStatus` 必须含 `AFTER_SALE`（或独立建「-售后」卡）。红区（退款/退货/换货/理赔/议价/投诉/物流异常处置）仍不做卡。
- **会话订单状态取数**：只能从**回放 trace** 取 —— `trace.orderState`（阶段级，如 `售前(未下单)` / `发货后`）+ `trace.orderStatusDesc`（具体状态）。`paginateV2` 与工坊列表的 `orderState` 字段常为空。

### ⛔⛔ 尺码类：不做知识卡，一律改「尺码表技能」(SIZE_CHART)（用户 2026-10-26 立规）

> 原话：「**尺码表的这一类是需要在技能里面更新的，这个是规则**」

**规则**：工坊记录命中「尺码 / 号型 / 多少斤穿什么码 / 身高体重怎么选 / 有没有大码 / 卡码 / 均码」→ **不进 §5 查重、不进 §6 写卡、不新建知识卡**，直接转 `tanyu-size-chart`（`/api/copilot/tool-base-card/*`，`type=SIZE_CHART`）做「建 / 改尺码表技能」。

**为什么（三条实测，不是偏好）**
1. **两条检索链**：尺码只走 SIZE_CHART 工具调用，知识卡里的尺码段喂不到这条链 —— 写多少段都答不出。§7.6 曾把「尺码表都有专段」当成已覆盖，该结论作废。
2. **300 字额度装不下**：M/L/XL/XXL 四档 + 身高体重交叉 + 卡码建议，塞进主体必然挤掉真正的佩戴指引。
3. **同组多套档位一段写不下**：实测 8 个高频组里 **4 组同组并存 2~4 套体重档位**，知识卡只能写一套 ⇒ 全组套用必错。两例已确认的错答都出自知识卡里的尺码段：`6a9279518895be0c087117ef`（恒源祥远红外护膝长款V2款-售前，拿艾草款档位套全组）、`6a6ffa77ca6c2f6e31aca7b0`（护腰网眼轻薄款-售前，整表比 SKU 少一档）。

**交接三步**
1. **识别并摘出**：命中词表 → 打 `SIZE_CHART` 标，从本批里单独归类，**不参与后续查重/写卡**。
2. **只读判现状**：`POST /api/copilot/tool-base-card/paginate-card {pageIndex:1,pageSize:500}` 拿全量；**⚠️ 列表只返回 id/title/type/ifOpen/lastUpdatedAt，不含 `includeCondition`，必须逐条 `detail {id}`**；看目标 spu 在不在 `includeCondition.spu`、组在不在 `productGroupId` → **有＝改技能；无＝建技能**。
3. **落地与验收**：优先 `includeCondition.spu` 逐款绑（一条技能只装一套档位）；同组多套档位按 `tanyu-size-chart` §五 分桶建多条，⛔ 不要用 `productGroupId` 一把套全组。验收 = `verify-sizechart.js` 独立进程回读 + 工坊同题回放能生成，再按 §7.5 点完成处理。

## 4. ③ 边界判定（硬门槛，不许跳）

依据《人工与智能体回复边界规则1.0》，**五维法**：信息确定性 / 处置权利 / 合规风险 / 情绪烈度 / 复杂性 —— **任一维命中红即归人工**。

- 🔴 **红区（本就不该由 AI 答）→ 不做卡**。动作改成「配转人工前置节点 + 在报告里列出」。典型：退款/退货/换货/补发/理赔/改单/指定快递/议价/物流异常处置/医疗诊断与疾病适配判断/投诉差评/索赔。
- 🟡 **黄区**：可做卡，但正文必须带「转人工兜底」条款。
- 🟢 **绿区**：正常做卡。

**实测提醒**：某店 4,037 条工坊问题里红区占 46.6% —— 意味着**待处理清单里近一半根本不该做卡**。先归区再动手，能省掉一半无效建卡。

规则全文在 `~/.workbuddy/skills/tanyu-knowledge-card/references/人工与智能体回复边界规则1.0.md`。

**反例（本公司实测踩过）**：给「腰椎间盘突出能不能用这款」做卡＝教 AI 做疾病适配判断，属红区；正确动作是「不作判断 → 建议遵医嘱 → 转人工」。

## 5. ④ 相似知识查重（决定"更新"还是"新增"）

**必须扫三类卡，只扫第一类会误判**：

1. 绑了本品商品分组的卡（`includeCondition.productGroupId` 含该组）
2. **跨组通用卡**（一张卡绑 15~33 个分组的，如「护腰医用及执行标准——售前通用」）
3. 全店同品类卡（按标题关键词）

判定口径：把这条问题拆成**意图**，看已有分段里有没有直接可用的答案段。

- 有相似知识 **且口径完整** → 这张就是"相似的知识"，**不新建**，走"更新/补充该卡"。
- 有相似知识 **但口径缺失或自相矛盾** → 在本品「-售前」卡里**新增分段**把口径补齐（§6）。
- 完全没有 → 新增分段到本品「-售前」卡。

### ⛔ 查重的致命误区：别用"关键词命中数"当覆盖证据

**关键词命中段落数会严重高估覆盖。** 实测把 11 条候选主题拿去全库正则扫：

| 主题 | 关键词命中段数 | 真实结论 |
|---|---|---|
| 垫片/三角/鬼脸 | 94 段 | **已覆盖**（「护腰赠品垫片」专卡已绑本组，段 3 写了三角形按摩垫片） |
| 尺码/大小号/体重 | 756 段 | 目标组**未覆盖**（那 756 段几乎全是别的商品组的） |
| 使用寿命/能用多久 | 302 段 | **已覆盖**（TM—护腰通用-售前 段 15「1–2 年」，绑 33 组含本组） |
| 厚薄/更厚 | 26 段 | **已覆盖**（同组 PDD 售前卡段 7 已写「普通款棉质、升级款复合面料更厚」） |

**正确做法（三读）**：① 关键词粗筛拿到候选卡 ID → ② **把目标组「-售前」卡的分段正文逐段读完** → ③ 把疑似覆盖的**专卡**（如垫片专卡、视频通用卡）分段也读完。只有两处都确实没管，才判真缺口。

实测 11 条候选里 **只有 5 条是真缺口**（约 45%）。**不做这一步就会有一半是重复建卡。**

**为什么优先"卡内新增分段"而不是新建卡**：用户明确要求过「写在探域的这个知识卡片中，点击新建分段」。而且同商品多卡并存会带来口径互斥 —— 实测某店 46 处口径冲突里大量来自"同一维度分散在两张卡"。

### ⛔ 动笔前必算：未生成密度 = 该组工坊条数 ÷ 该组已绑卡数（2026-09-29 实测）

**未生成条数多，未必是缺知识——很可能是「卡有、但没绑到这个组」。**

实测某店 195 条未生成，按组算密度后根因一目了然：

| 分组 | 工坊条数 | 已绑卡 | 条/卡 |
|---|---|---|---|
| 护腰网眼环抱6支撑D款 | **82** | **3** | **27.3** ← 异常 |
| 护腰柔韧纤翼D2款 | 11 | 3 | 3.7 ← 偏高 |
| 静脉曲张压缩袜（中筒+长筒） | 34 | 19 | 1.8 |
| 护腰环抱支撑D款V2款 | 13 | 23 | 0.57 ← 正常 |
| 护腰经典腰托D款V2款 | 11 | 22 | 0.50 ← 正常 |

⛔ **但"补绑"的收益必须用宽口径重算，不能只看绑组数**（2026-09-29 推翻本节旧结论）：
- 旧结论「17 张护腰族通用卡漏了两个新组 → 补绑可覆盖 120 条(61.5%) / 124 条」**作废**。它只把「绑了目标组的卡」算进覆盖池，漏掉了**全店级卡**——`includeCondition` 的商品维度（`spu`/`shop`/`rules`/`productGroupId`/`sellerGroup`）**全空 = 不限定 = 全范围**，配 `platform` 空或含 1 就是**全 PDD 店生效、不需要绑组**（本账户 81 张这类卡）。
- 宽口径复核（脚本 `net-gain.js`）：目标组 134 条现状**已覆盖 124 条**（只算绑组卡是 108 条），补 19 张非 TM 候选卡 **净增 0 条**；真缺口只剩 10 条，其中 9 条是会话语境碎片。
- → **教训：「条数 ÷ 绑卡数」不是缺口信号**，只反映绑组数。要测收益必须走 `现状覆盖池 → 加候选卡 → 取差集`。
- ⛔ **TM/天猫卡一律排除**（用户 2026-09-29 定：TM 是产品知识、归天猫，**不准绑到 PDD 分组**）。25 张候选里 6 张是 TM 卡，其中最大的两张 `TM—护腰通用-售前`（33组/28段）、`TM—护腰通用-售后`（33组/12段）必须先剔除；它们与同名非 TM 卡主题重复，是 PDD 组「口径互斥」的根源。

工具：`jx-group-cards.js`（组→已绑卡）/ `jx-coverage.js`（意图×覆盖判定）/ `jx-rebind.js`（跨组通用卡补绑推荐）/ `jx-rebind-impact.js`（补绑可解决条数测算）/ `jx-dump-heads.js`（dump 指定卡各段首行）/ `net-gain.js`（**宽口径净收益测算，出结论前必跑**）。
判断口径：**不是关键词命中就算覆盖**，也不是"绑了组才算覆盖"——覆盖池 = `productGroupId` 含本组的卡 **∪ 商品维度全空的全店级卡**，**排除 TM/天猫卡**。

## 6. ⑤⑥ 生成话术 + 卡内新建分段

### 话术结构（固定五项，来自 `customer-service-script-card`）
`触发条件/适用场景` → `相关指引` → `示例回复一`（正式亲切）→ `示例回复二`（口语化）→ `回复规则`

探域落地形态（已定稿，别改）：
- **一个分段 = 一个知识主题**，把「触发条件＋相关指引＋回复规则」写在同一段正文里；
- **示例回复一/二 放进 ```` ```text ```` 文本框块**（后台是"打斜杠选文本框"），**文本框不计入 300 字额度**；
- 计入额度 = 去掉 ```text 块、去掉空白后的字数，**必须 ≤ 300**（保守算法，服务端可能重算得更小）；
- 正文**严禁内部批注**（"待回填""以本卡为准"之类一律剥离）。

### ⛔ 示例话术标点硬规则（拼多多质培端，2026-09-25 起）

**示例话术内不得出现 `。` 和 `！`** —— 它们是结束符号，智能体会自行按它分段把话术逐条发出，分段一多重复率升高、变成敷衍对话。

- 全句用 `，` 顺连，句末用语气词收尾（哈／哦／呢／啦／～），不落句号
- 问号也尽量少用，问句改陈述＋引导
- 落库脚本加硬校验：`if (box.includes('。') || box.includes('！')) process.exit(1)`
- 这条只约束**会被直接发出去的示例话术**；触发条件／相关指引／回复规则不受限

> 落地提醒：本条是**新增的**，存量卡里的示例话术普遍带句号。新写分段必须遵守；存量卡由用户决定是否批量清洗。

### 落库（关键：卡内追加，不是新建卡）
- 脚本模板：`tools/append-lw2-seg.js`（`--dry` 预览）+ 正文文件 `tools/card-lw2-seg.md`
- 核心：读-改-写，`content = 原content.map(x=>({id,content,chunkLength})).concat([新分段])`，必带 `id + lastUpdatedAt`
- **沿用原卡 `labels`，绝不用本地标签地图**（实测本地 `kc-tags-map.json` 的 ID 与线上真实值**普遍差 1 位**：售前 `…c7af`→实际 `…c7ae`、护具类 `…d054`→实际 `…d053`。正确做法是从线上卡的 `labelInfos` 取，或直接沿用目标卡自带的）
- 剔除只读字段：`labelInfos / source / productCondition / ifHasUrl / urlInfos / ifOpenSync / createdAt`
- 追加前先备份原卡 content（`tools/card-*-backup-before-append.json`）
- 追加前先做幂等检查（扫原卡是否已有同主题分段）

### 核验清单（缺一不可）
- [ ] 回读卡：分段数 +1、新分段有独立 `id`
- [ ] `chunkLength ≤ 300`（以服务端回读值为准）
- [ ] `chunkLearnStatus` 由 `WAIT` → `FINISH`（实测 10 秒内）
- [ ] 原分段 cl、标签、分组、平台、启用状态**零变化**
- [ ] 截图后台（编辑面板滚到底能看到新分段）

## 7. 什么算「这条得以解决」

**不是**工坊那条记录的 `reviewStatus` 变了 —— 补卡不会自动回写工坊记录。定义是：

> 该商品该场景**已有可被检索命中的知识分段**，AI 下次遇到同类问题能直接作答，不再落入"话术未生成"。

核验方式：下次跑同一支 `workshop-pending.js`，看该商品/该意图的条数是否下降；或在工坊用同问题回测 AI 是否已能答。

## 7.5 另一条正规路径：场景回放 + 完成处理（2026-09-29 打通，**动笔写卡前先走这条**）

⛔ **先别急着补卡**：实测 395 条「话术未生成」里 **290 条能跑成回放，其中 193 条（66%）今天用当前知识库就能重新生成内容**。
说明这批「未生成」大部分**不是知识缺口**，而是当时的检索/配置瞬时问题（可自愈）。**用回放验证过再决定是否写卡**，能省掉大量白写的卡。

### 接口（纯 API，不用点 DOM）
| 动作 | 请求 |
|---|---|
| 启动回放 | `POST /api/im/agent-scene-replay/start` body `{cardId, thirdShopId}` → `data.replayId` |
| 查回放结果 | `GET /api/im/agent-scene-replay/detail?thirdShopId=&replayId=` → 轮询到 `replayStatus=SUCCESS`，**重新生成的话术在 `data.trace.content`** |
| 取最近一次回放 | `GET /api/im/agent-scene-replay/latest?thirdShopId=&cardId=`（`data:null` 表示没跑过） |
| **完成处理** | `POST /api/im/agent-trace/review` body `{cardId, thirdShopId}` |
| 反查处理状态 | `POST /api/im/agent-trace/trace` body `{cardId, thirdShopId}` → `data.reviewStatus`（**1=待审核 / 2=已处理**） |

`cardId` 就是工坊记录里的 `id`（即"追踪ID"＝"主题ID"），**不是知识卡 id**。

### ⛔ 场景回放有「每日次数上限」（最重要）
超限后 `start` 返回 **HTTP 200 但 `msg=「今日场景回放次数已达上限」`** —— **不是超时、不是失败**，重试无用。
- 平台实测上限约 **300 次/天**；**用户 2026-10-10 立的作业预算：100 次/天，超出即停**。
- ⭐ **回放前必须自判「是否真需要回放」**：先取非回放证据（卡 `orderStatus` / 关键词 / 分组绑定 / 历史同题 / 语义边界），**只对决策关键且非回放无法判定的条目回放**。
- 跑批前先小批（≥5 条）试探额度；
- 批量脚本必须**增量落盘 + 按 id 跳过**，超限的次日续跑即可。
- ⚠️ `replay-ids.js` **必须显式传 `--ids`**（只给 `--idx` 会打印用法并退出，不消耗次数）；`--idx` 仅用于元数据查询。

### 判定口径（保守侧，未获用户明确口径前一律用它）
- ✅ **点完成处理**：内容给出了与提问**直接相关的信息/参数/流程/步骤/结论**，或按边界规范把红区诉求**明确导向专员/医生**。
- ✗ **只记录**：纯共情、纯复述（"您刚才提到的…咱们接着聊"）、纯占位（"我帮您看看"、"我在的呢"）、**越权承诺**（如 Agent 直接答应 20 元补偿 —— 属红区，反而不合规）。
- 泛化开场白（"亲，我帮您看看这款怎么选更合适"）→ 归**只记录**，宁可少点也别错点。
- ⚠️ **字面相似度不能当判据**：语义相关的长句（如"质疑虚假宣传"→"要求提供宣传截图核实"）Jaccard 可能只有 0.016。`judge-replay.js` 的 score 只用来排序提示，**判定必须人读**。

### ⭐⭐⭐ 清收口径（用户 2026-10-12 定，放宽，优先于上面的保守侧）
> 原话：「**回放成功后，可以点击完成处理，然后不用做卡的也可以完成处理**」

1. **回放成功的 → 可以点完成处理**；
2. **判定「不用做卡」的 → 也可以点完成处理**（不必等回放、不必先补卡）。

**含义：把「工坊记录状态」与「是否补卡」解耦** —— 补卡是知识库动作，完成处理只是标记这条记录已看过。不做卡的记录（红区／会话碎片／已覆盖／量级极小）可直接清掉，**后续任何时候补卡依然生效**，不存在"清了就不能补"。
- **唯一例外（不点完成）**：红区里的**越权承诺**类（Agent 答应补偿金额／改单／指定快递等）宁可留着，也不要点完成 —— 点了等于把越权话术训练成「正确」。
- 清收**不消耗场景回放额度**（回放与完成处理是两个独立接口），所以大批量清收可以直接做。
- 清收后**必须独立核验**：重拉同一天同一筛选池，看 total 是否归零（脚本 `verify-handle-1011.js`）。

### ⭐⭐⭐ 报数务必写清是哪个口径（2026-10-12 实测）
清完「作业口径」（`type:['CONSULT_REPLY'] + reviewStatus:1 + noSendReasonList:[114]`）之后，**把话术类型放开再看，同一天同一批店还剩一大批**：
- 实测 10-11 五家重点店：作业口径 244 条 → 全部处理完归零；**不限话术类型仍有 881 条**（s1 585／s2 5／s4 114／s23 126／s23x 51）。
- 两类是 `CONSULT_REPLY`（咨询回复）与 `CONSULT_PRODUCT`（商品咨询），**后者约占未生成总量的 84%**。
- ⇒ 任何"待审核还剩多少"的结论，必须标明口径；否则一放开类型，数字会大好几倍。

### ⛔ 跨店跑批必须用多店版（2026-10-02 补）
`replay-batch.js` / `handle-batch.js` 把 `SHOP` 和 `SRC` **写死成单店**，跨店直接用会把别店的 `cardId` 发给错误店铺 → 要么 start 失败要么处理到错误的记录。多店场景改用：
```bash
# 输入 nogen-3shops.json（每条自带 shopId / tag / shop）
node tools/replay-3shops.js --limit 5 --concurrency 2   # 小批验额度
node tools/replay-3shops.js --concurrency 3             # 全量，增量落盘可续跑
node tools/set-decisions-3shops.js                      # 人工判定写回
node tools/handle-3shops.js --dry                       # 预演
node tools/handle-3shops.js --concurrency 2             # 执行
node tools/verify-3shops.js                             # 独立核验（重拉池比对）
```
**核心改动：`shopId` 从每条记录自带字段取**，不再用全局常量。落盘记录里务必带上 `shopId`，否则处理阶段不知往哪家店发。

**自愈率两次实测**：器械保健店 193/290 = **66%**；三家店（伊藤源 / PANAPOPO医疗健康官方 / moffe筑越）24/41 = **58.5%**。**同一量级 ⇒ 每次跑批前先回放，能清掉过半积压，不必逐条补卡。**

**⛔ 红区记录的回放产出通常是「纯共情」或「越权承诺」**（实测如改址场景答"正在为您提交修改申请"、改码场景答"马上帮您核实"）。**这类即使出了内容也不得点完成** —— 点了等于训练 AI 越权。判定时把「是否承诺了 AI 无权执行的动作」列为否决项。

### 买家标识（用户要「加一列买家昵称好核对」时看这里）
⛔ **探域没有人类可读的买家昵称**（不存在"小鱼儿"这种），买家唯一标识是**买家账号** `buyerAccount`（一串数字，如 `5597926210`）。
- `POST /api/im/agent-trace/paginateV2` 的返回里**本来就有** `buyerAccount` —— 自写拉数脚本别只挑固定字段把它裁掉（**我们踩过这个坑**）。
- 会话上下文 `GET /api/im/agent-trace/get-card-chat-context?thirdShopId=&cardId=`（**GET**；用 POST 会返 `{code:0,msg:"系统繁忙"}`）里字段名叫 `buyerNick`，**值与 `buyerAccount` 是同一串**。
- 工坊详情面板「基础信息 → 买家」显示的就是这串数字 → 可直接作逐条核对凭据（配合记录 `id`）。
- **一次拿全**：`pull-nick-map.js` 去掉 `reviewStatus` 过滤，即可同时覆盖待审核+已处理（实测该店 590 条；待审核 253 + 已处理 337）。

### 两个操作坑
- ⚠️ **同一 persistent profile 不能开两个 Chrome 实例**：批量跑批期间另起探查/反查脚本必定启动失败。要反查就等跑批结束。
- ⚠️ 工坊「搜索买家提问/生成话术内容」输入框**不是即时生效**（填值 + input/change 事件不触发查询），拿它定位记录会点错行。要定位某条记录：**先确认列表首行文本命中目标再点**，或直接走 API。

## 7.6 「回放后仍未生成」怎么办：先诊断，别急着补卡（2026-09-29）

对回放 `SUCCESS` 但 `regenerated=false` 的记录，用户会问「能不能做张卡让它生成」。
**必须先回答「知识库里到底有没有」，再回答「能不能做卡」** —— 实测 97 条里 59 条题目可做卡，但大多数知识**库里已经有**（上下朝向、佩戴时长、清洗、尺码表都有专段，且分段学习状态全 `FINISH`）。**直接补卡会白写。**

**三步诊断**
1. **分桶**：`classify-nogen97.js` —— 三桶「可做卡 / 红区 / 会话碎片」，人工逐条判定后落盘。
   实测分布：可做卡 59（佩戴方向 19 / 支撑等级 13 / 参数 10 / 使用场景 10 / 其它款 7）｜红区 27｜碎片 11。
2. **问题 → 商品 → 分组**：`probe-spu-groups-batch.js`（走 `product-paginate-with-product-group` 的 `spuIds`，一次可传 20 个）。
   ⚠️ **`goods-skus-full.json` 只含 PANAPOPO旗舰店的商品**，拿别的店的 spuId 去查会全部落空——必须走接口现查。
3. **该组卡池 → 逐段读**：`coverage-nogen97.js` 列出「组 → 卡 → 段首行」；`check-learn-status.js` 看分段学习状态与绑组。
   判定池 = 本组已绑卡 ∪ 全店级卡 − TM 卡。**关键词命中不算数，必须人读原文。**

**判定就看三件事**
- ① 该组卡里**到底有没有**这个答案（有 → 属检索未命中，补卡无效）
- ② **卡内是否自相矛盾**（同卡两段口径打架，智能体取信哪段都不确定）
- ③ 知识是否**错组**（答案在别的组的卡里，对本组不生效）

**三类典型病（实测）**
- **通用卡漏绑新组**：`如何区分上下-护腰通用` `69e0ad85fd984b133827fdb3` 绑 13 组，全是 4–6 月老组，独缺 8 月新建的「网眼环抱 6 支撑 D 款」「柔韧纤翼 D2 款」。
- **等级知识错组**：完整等级说明在 V2 款组卡里，而问「13级/9级/6级」的商品属网眼环抱 D 款组，该组 3 张卡零等级内容 → 真缺口。
- **主卡自相矛盾**：`6a75a9ebca6c2f6e31adccf1` 段2「内置 6 块矩形仿生钢板」vs 段4「内置 4 根钢板支撑条」。

**动作优先级**：修卡内矛盾 ＞ 补本组真缺的知识 ＞ 补绑通用卡 ＞（暂缓）补已有知识的段落。
**改完必须重跑回放验证同一批 id**，对比生成率；**若仍不生成，瓶颈就在检索／触发词／Agent 配置，不是知识覆盖** —— 别继续补卡。

**⛔ 查「级数」这类参数类知识，事实源只有 SKU 款式规格**（2026-09-29 实测）
- 脚本：`node tools/probe-spu-skus.js <shopId> <spuId1,spuId2,...> [out.json]` → 读 `skus[].attrs` 里「款式」的值。
- 实测店铺口径 **级数 = 支撑条数量**：`医用基础【4软钢支撑】` = 5 级 ／ `【5软钢支撑】` = 9 级 ／ `【6椎骨支撑】` = 13 级；旁证另一批 SKU `【5级支撑】…5根支撑`、`【2级支撑】…无支撑`。
- ⚠️ **同款商品会同时卖多个支撑规格**（本案 4／5／6 根三个 SKU 同在售）→ 卡里出现两种钢板数量**未必是写错，可能真是两个规格**。改前务必查 SKU，别直接删数字了事。
- ⚠️ 全库「N 级」**各款一套口径**（1/6/9 级、6/12 级、15/8 级、20/10 级、3/12 级都出现过），**不可跨款归纳**。
- 详情页只能印证结构（`穿戴步骤`图、`腹部宽10cm／腰部宽16cm`），**不会写上下朝向**；朝向类知识若无图示，**沿用店内既有通用卡口径，不要自行编造**。

⚠️ 全库 928 张卡 `ifOpen=true, ifLearning=false` 是**常态**（919/928），**不代表卡不参与检索**；5208 段学习状态全 `FINISH`。**别把它当成故障来解释"召不回"。**

## 9. 坑清单（都是实测踩过的）

1. **reviewStatus 别猜**：**`=1` 才是「待审核」，`=2` 是「已处理」**（别按字段名反推，见坑 14）。完整「话术未生成」口径 = `type:['CONSULT_REPLY'] + reviewStatus:1 + noSendReasonList:[114]`（§2）。只看 `ifSend=false` 会多捞 260 条（那是已生成但未发送，性质完全不同）。
2. **查重只查绑本组的卡 → 误判成"缺口"重复建卡**。必须带上跨组通用卡。
3. **服务端会重算 chunkLength**：客户端传 288，回读先 288、数分钟后变 252。本地公式是保守上界，对外报数用服务端值。
4. **标签 ID 别用本地地图**（差 1 位，见 §6）。
5. **红区占比接近一半**，先归区再动笔。
6. **别把"补了卡"说成"工坊记录已解决"**（§7）。
7. **绿区 ≠ 待办**：词表只能初筛，89 条里 24 条未命中规则，人工过完有 6 条该剔除/降红。做卡前必须逐条过（§2）。
8. **定位商品分组别用按热度截断的快照**：旧快照只有 185 款，漏 18 条。用 `goods-fetch-full.js`（8,636 款）。（§2）
9. **卡标题的分组名常在括号里**（「膝部固定器（弧形护膝绑带P款）-售前（PDD）」），归一化匹配时**不能删括号内容**，否则本品卡被误判成通用卡。（§2）
10. **同名卡可能一张绑组一张没绑**：实测「膝部固定器（弧形护膝绑带P款）-售前（PDD）」线上有两张，一张绑本组、另一张 `productGroupId=[]`（未绑任何组）。**未绑组的那张分组卡永远召不回，但全店级检索仍会命中它** → 与本品卡打架。写卡前先看候选卡是不是"组数=0"。发现这种重复卡**只列给用户拍板，不自行删**。
11. **商品详情页已打通（2026-09-25 推翻旧结论）**：免登录参数 `https://mobile.yangkeduo.com/goods.html?goods_id=<spuId>&_x_no_login_launch=1` 可直出页面（URL 会追加 `uin=`），**不需要扫码**。
    - 必须复用有 cookie 的 profile（`.../work/pdd-buyer-profile`）；**全新 profile 会卡死在手机号验证码页**（H5 无二维码入口）。首访若跳 `login.html`，等 30~60 秒或点"返回"即自动进 goods 页。
    - 详情图文＝懒加载长图（790 宽系列），须慢滚 30 次触发，再抓 `img src`。脚本：`tools/pd-detail-imgs.js <spuId>`。
    - 商家后台 `mms.pinduoduo.com` 仍被滑块拦下，未打通。
    - **事实源优先级**：详情页图文（宣称/参数/尺码表）＞ 商品库 SKU 全属性 ＞ 工坊咨询原话。详情页是"宣称 vs 实际"冲突的唯一证据源。
12. **工坊接口深翻上限约 1 万条**：第 21 页起返回空。总量超限时静默漏数。**先跑 `probe-total.js`；total ≫ 实拿量就改 `workshop-pending-slice.js` 时间切片。**（注：加了服务端筛选后总量通常不大，反而不容易触发；全量拉取时才要小心。）
13. **"未生成多"别急着归因"漏绑"，更别急着写卡**（2026-09-29 两次修正）：
    - 先算「条数 ÷ 已绑卡数」找**绑组异常**的组（>3 值得看一眼），但**它只是线索、不是缺口信号**。
    - 判断是不是真缺口，必须跑宽口径覆盖：`现状覆盖池（绑本组的卡 ∪ 商品维度全空的全店级卡，排除 TM）→ 加候选卡 → 取差集`，脚本 `net-gain.js`。
    - 实测器械保健店 395 条 / 两个"只绑 2~3 张卡"的组：按旧口径"补绑 25 张可覆盖 124 条"，宽口径复核后**净增 0 条**（全店级卡早已覆盖 124/134），真缺口仅 10 条且 9 条是会话碎片。
    - → **"未生成"常常不是知识缺口**（可能是检索未命中 / 卡粒度 / Agent 配置）。报"补绑可解决 N 条"之前必须先跑净收益测算。
14. **⛔ 别按字段名猜语义——本次最大的坑**（2026-09-29）：`reviewStatus=2` 被想当然当成"待审核"，实际是"已处理"。凭"content 为空且未发送"这个特征去反推，特征自洽但语义正好相反。**必须用 UI 逐项点选 + 抓请求体来确认参数语义**，或按用户截图原样复现到数值一致。这次错误导致整份分析（195 条）口径全错，正确是 395 条。
15. **工坊 UI 的三个显示陷阱**：① 页面默认窗口是**近 30 天**（不是本月 1 号起）；② 打开时默认选中**上次那家店**，不是用户在说的那家；③ 左下角「共 N 条数据」是**当前筛选下的 total**，不选筛选就是全量。用户凭页面截图报数时，这三条必问/必核。
16. **口径对不上时的工作顺序**：① 先抄用户截图里的**每一个筛选条件** → ② 用有头浏览器把筛选项**真的点一遍**、抓 `paginateV2` 请求体（`probe-ui-status.js` / `probe-filters.js`） → ③ 写复现脚本调到数值完全相等（`probe-repro395.js`） → ④ 再动分析。**先复现，再分析。**
17. **一次追加多段要用 `append-multi-segs.js`**：目标卡更新时间早、不在列表首页时，`pageIndex=1` 那套找不到卡 → 必须**游标遍历**（实测 3 轮 300 张命中）。该脚本支持 `--card <id> --segs 0,1,2,3`，内置字数与标点硬校验、自动备份原卡、回读复核。
18. **⛔ 标题带 `TM`/`天猫` 的卡不准绑到拼多多分组**（用户 2026-09-29 明确）：TM 前缀卡是天猫产品知识，拼多多店不该用。

    - 全库 152 张 TM 卡里有 3 张**已误绑 PDD 组**（`TM—护腰通用-售前` 13 个 PDD 组 / `TM—护腰通用-售后` 14 个 / `TM-护膝通用-售后` 14 个），与同名非 TM 卡主题重复 → 是 PDD 组「口径互斥」的根源，**发现只列给用户拍板，不自行改绑**。
    - 反向也有坑：非 TM 但商品维度全空的**全店级卡本来就全 PDD 店生效**，不要在"覆盖池"里漏算它们（见 §5 与坑 13）。

19. **被质疑「这张卡你改了吗／绑了吗」时，用服务端字段自证，别凭印象答**（2026-09-29）：
    - 跑 `tools/probe-rebind-audit.js` —— **动作审计三问**：① 目标分组当前绑卡清单（含 `lastUpdatedAt`）② 候选卡是否已绑进目标组 ③ 全库今天被改动过的卡。一次全量快照出铁证，成本约 1 分钟。
    - 单卡细查用 `tools/probe-card-detail.js <cardId> [<id2>…]`：输出标题 / `createdAt` / `lastUpdatedAt` / 各分段首行 + cl + 学习状态 / 绑组 / labels。

20. **⛔ 别把接口返回「裁成固定字段」再落盘**（2026-09-29）：`pull-consult-nogen.js` 早期版本只挑了 id/question/spuTitle 等固定字段写进 json，把 `buyerAccount` 丢了。后来用户要"加一列买家昵称好核对"，才发现**接口本来就有**，白跑一轮探查。

21. **`labels` 与 `labelInfos` 是两回事，别混着比**（2026-09-29）：

22. **全库快照差分审计会漂移 1~2 张**（游标分页）：`kc-live.js` 偶尔报 `total=928 抓到=927`。做「今天改了哪几张卡」的差分时，**接受这个噪声**，对被漏抓的卡单独用 `probe-final-verify.js` 兜底确认。
