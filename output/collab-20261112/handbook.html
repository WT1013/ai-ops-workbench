一、迁移总览：三条通道的职责

改造后，一个工作台的运转由三条通道组成，各管一件事，互不干扰。

通道承载什么谁能改怎么生效
代码仓库
GitHub 私有		页面结构、样式、业务逻辑、数据源文件项目成员（走 PR）合并到 main 后由发布人构建发布
CSV 数据源
data/*.csv		店铺、账号、指标等批量业务数据数据负责人（单人独占）提交 + 发布后，所有人页面 60 秒内自动刷新
云端库
Supabase		界面上随手改的内容、目标值、文案、自定义代码拿到编辑码的成员保存即写库，其他人 60 秒内拉到

外部访问者只走“读”的一侧：打开链接就能看到全部页面与数据，但没有任何写入口。

为什么不全放数据库？批量数据（比如 291 条账号）在页面里一条条改不现实；放在 CSV 里可以用 Excel 批量编辑、有 git 历史可回滚、谁改的一目了然。而日常的状态与备注改动放界面更快。两条通道按“谁更晚谁生效”合并，后文第五节说明。

三、权限规则

权限必须三层同时设，缺一层就会漏。

3.1 第一层：代码仓库（谁能改代码）

  1. 仓库保持 Private。
  2. Settings → Manage access → 给成员 Write（不要给 Admin）。
  3. Settings → Branches → 给 main 加保护规则：
勾选项作用
Require a pull request before merging禁止直接推 main
Require approvals: 1至少一人看过
Dismiss stale approvals…有新提交就重新评审
Do not allow bypassing管理员也要走 PR

发布权只给项目管理员一个人。

3.2 第二层：项目团队空间（谁能改资产）

角色网盘权限边界
项目管理员可编辑上传发布包、维护文档
项目成员可编辑上传自己的产物、更新数据副本
外部协作者不加入 / 仅查看只给网页链接，不给网盘
团队空间里不放数据库密码、API 密钥、团队编辑码。空间是共享的，一旦放了就等于全组公开。

3.3 第三层：应用内（谁能改数据）

谁能看到能改怎么进
外部访问者全部页面与数据什么都不行直接打开链接
项目成员同上数据 / 文案 / 页面 / 自定义代码右上角徽标 → 输团队编辑码
项目管理员同上以上全部 + 发布同上 + 仓库权限

实现方式：

  • 默认只读。新增 / 编辑 / 删除 / 导入 / 保存按钮不渲染；表格点了不进入编辑态；即使用脚本调用写方法，数据层也会拦截并提示。
  • 编辑码只存哈希。代码里只有 SHA-256 值，没有明文；换码 = 改哈希 + 重新发布。
  • 状态记在本机。换设备、清缓存都要重新输码；点徽标可随时退回只读。
边界必须讲清：前端只读是“软闸”，挡的是链接被转发后别人随手乱改，不是防内行攻击——浏览器端持有的是 Supabase 的 publishable key。若要做到“后端强制只允许登录成员写入”，需开启 Supabase Auth 并把写策略从 to anon 改为 to authenticated，代价是成员需要登录一次。具体 SQL 见 MIGRATION.md 第 3.4 节。

四、数据源实时同步

4.1 机制

  1. CSV 与页面一起发布在同一个站点下（/data/）。
  2. 构建时把 8 张表的内容算一个哈希，写进 data/manifest.json（版本号 + 发布时间 + 各表行数）。
  3. 页面启动读一次 CSV；之后每 60 秒只拉这份几百字节的清单。
  4. 版本号变了 = 有人改了 CSV → 自动重新拉取全部 CSV → 合并 → 重渲染。切回标签页也会立刻检查一次。

所以成员改完 CSV 并提交发布后，所有人不用刷新，60 秒内页面自己变。

4.2 合并规则（防覆盖的核心）

情况结果
CSV 行，界面没改过用 CSV
界面改过，且改动时间晚于 CSV 发布时间保留界面版本，不会被下次发布盖掉
界面改过，但 CSV 之后又更新了CSV 赢（以最新发布的表为准）
CSV 里删掉某行该行若来自 CSV，页面同步删除
界面新建的行CSV 永远不会删它
历史遗留、没有来源标记的行一律保留，绝不因一次同步丢数据

4.3 实践建议

  • 批量数据（店铺、账号、指标）走 CSV，一次改一批，有 git 历史可回滚。
  • 日常小改（状态、备注、负责人、目标值）走界面，快，且不会被下次 CSV 覆盖。
  • 不要在同一批里既改 CSV 又在界面改同一行——谁赢取决于时间，容易互相疑惑。
  • CSV 的 id 与表头不能改；改了等于删旧行 + 加新行，界面上的历史改动会丢。

五、重新发布流程

只有一条路径：改源码或 CSV → 本地构建 → 推送 main → Pages 自动更新（1–2 分钟）→ 链接不变。

5.1 只改数据（最常见）

git pull --rebase
# 编辑 data/shops.csv（Excel / 文本编辑器，存 UTF-8 逗号分隔）
npm run build          # 生成新的数据清单（版本号 = 内容哈希）
git add data docs dist
git commit -m "data: 更新店铺表 · 新增 3 家抖音店"
git push

5.2 只改页面或逻辑

git pull --rebase
# 改 src/js/ 或 src/styles/ 里对应模块
npm run check && npm run build
npm run test           # 功能回归
npm run test:collab    # 权限与数据源回归
git add -A
git commit -m "feat: 数据看板增加响应时长列"
git push

5.3 改连接配置

只改 config/app.config.json（云端地址、表名、轮询间隔、连接器、编辑码哈希），重新构建发布即可，不碰代码。

5.4 发布后 30 秒自检

  1. 打开线上链接 → 右上角是“只读预览” → 没有黄色提示条 → 设置页的数据源版本与刚发布的版本一致。
  2. 点徽标输码 → 变“成员编辑” → 改一个目标值 → 换一个浏览器打开，60 秒内能看到。
  3. 七个页面都能进，控制台无报错。

5.5 回滚

git revert <坏提交的 sha> && npm run build && git push

1–2 分钟回到上一版。切勿用 git push -f，会把别人的提交一起冲掉。

六、多人修改防覆盖

6.1 代码层

规则做法
一文件一人按模块分工表认领；改别人的模块先在群里说一声
先拉后推动手前 git pull --rebase，提交前再拉一次
小步提交一次只做一件事，标题写清“改了什么、为什么”
走 PRmain 开保护，所有改动经 PR + 1 人评审
冲突处理CSV 冲突按整行取舍；JS 冲突保留双方逻辑后跑 check，禁止 -X ours/theirs 一把梭
单一出口只有管理员能合并 main 并发布，避免两人同时发布互相盖产物

6.2 云端层

  • 只做行级差分写入，只推变化的记录，不整库覆盖。
  • 每行带改动人（updated_by）与时间（updated_at），出问题能追到人。
  • 拉取有保护：正在输入、弹窗打开、刚提交 2 秒内，都不会被远端刷新打断。
  • 冲突策略是“最后写入者胜”，没有字段级合并——所以同一行不要两个人同时改。

6.3 版本与留痕

  • 每次发布在 CHANGELOG.md 记一行：版本号 / 改了什么 / 谁改的。
  • 源码包带版本号，团队空间旧包不删，出问题能拿到任意历史版本。
  • 数据源版本号是内容哈希，发布日志里能看到“这次发的是哪一版数据”。

七、日常检查与应急

7.1 每周检查

检查项怎么查
线上是否是新版设置页看数据源版本 + 版本号
数据行数是否正常npm run build 输出各表行数，与预期比对
权限是否仍然生效隐身窗打开链接，确认是“只读预览”、无写按钮
云端是否连通页面顶部无黄色提示条

7.2 常见问题

现象处置
改了 CSV，页面没变检查是否执行 npm run build、docs/data/manifest.json 版本是否变、是否 push 成功、等 60 秒
徽标点不开 / 输码无反应必须用 https 或 localhost 打开，file:// 双击打不开编辑模式
顶部黄色提示条云端未连通（多是还没跑建表 SQL）；此时改动只存本机，恢复后自动补传
