3. 技术架构与数据模型

3.1 架构

  • 前端：单文件 HTML（约 282 KB），内联了云服务 SDK、样式和全部逻辑，无构建依赖、无外链 CDN，打开即用。
  • 后端：WorkBuddy 云服务托管的后端（Postgres + PostgREST 风格接口 + WorkBuddy OAuth），不用自己运维服务器。
  • 身份：WorkBuddy 账号 OAuth，或邮箱验证码。未登录只能看到登录页。

3.2 数据模型

只有两张表，简单到不需要 ORM：

表关键字段说明
wb_recordskey（主键）、coll、rec_id、data（JSONB）、updated_at一条业务记录一行，coll 区分集合，data 存整条记录
wb_kvk（主键）、v（JSONB）全局配置，目前只存一条 meta（库版本、播种时间）

coll 取值共 8 个集合：shops（店铺）、accounts（账号）、metrics（指标）、tasks（任务）、qc（风控）、assets（资产）、apis（接口）、alerts（预警）。

3.3 同步机制

  • 登录后一次性把全量记录拉进内存（分页，每页 1000 行），页面渲染走内存，所以切页很快。
  • 写操作只推差分：客户端保留一份「上次同步时的快照」，只 upsert 变化过的行、只删除消失的行，不会整库覆盖，因此不会把别人刚改的数据冲掉。
  • 保存做 300 毫秒防抖，批量 200 条一次提交。
  • 冲突策略是后写覆盖（同一条记录同一时刻两个人改，后提交的赢）。团队规模小，够用；如果要严谨，需要加版本号与合并逻辑。

4.2 权限设计（重要）

  • 两张表都开启了行级安全（RLS），策略只授予登录用户组 authenticated，规则是「团队共享一份数据」：USING (true) WITH CHECK (true)。
  • 匿名角色 anon 的授权已全部收回。未登录访问数据接口会直接返回 permission denied，这是预期行为，不是故障。
  • 所以：链接不能随便发到外部群——登录页谁都能打开，但没登录读不到任何数据；想限制范围，靠不传播链接 + 账号体系。

6.1 v4.2 的特殊说明（别踩回去）

上一版做过一套「口令保险箱」：密码用 PBKDF2 + AES-GCM 加密后存云端，输口令才能看。后来业务判断不需要密码了，于是整块下线，包括加密逻辑、解锁弹窗、显示/隐藏密码、自动上锁、Excel 密码导入，以及配套的浏览器 xlsx 解析器。

  • 云端存量账号里的 pwd、hasPwd、完整 phone 字段已用 SQL 删除，并按原手机号生成 tail（后四位）。校验结果：291 条中残留旧字段 0 条、290 条有合法四位尾号。
  • 加密密文那一行（wb_kv 中 k='vault'）已删除，现在 wb_kv 只剩 meta。
  • 构建脚本里加了一道闸：产物中一旦出现 data-pwd、openVault、vaultPersist、__parseXlsxRows 或任何明文密码字面量，构建直接失败。不要为了「方便」把密码功能加回来，这是业务明确决定。

7. 还没做完的事（交接重点）

按优先级排列，前两条建议接手第一周就处理掉。

P0 · 统一入口，下线旧链接

目前存在两个可用地址，各自连的是不同且互不相通的数据库：

链接状态处置建议
...ai-ops-workbench-43332...?sharecode=L6I6SZYJ54新，正式入口保留，发给全组
...shop-ops-workbench-22038...?sharecode=DZ3YDH54UE旧应用，仍在线，库是空的建议下线，避免有人误用旧链接录数据后「找不到」
风险：两个环境的店铺数据不会互相出现。如果有人用旧链接录了数据，你在新链接里看不到，而且不会报错——只是「凭空消失」。发现数据少了一块，先确认对方用的是哪个链接。

P1 · 补齐其他平台的账号

291 条账号全部是拼多多。天猫、京东、抖音三家平台共 33 家店铺「有店无账号」，店铺库里显示为「缺账号」。需要各平台负责人提供账号清单后补录（按「角色 / 登录账号 / 绑定人 / 尾号」四条填即可）。

P1 · 接入真实指标数据

数据看板的 28 条指标是示例值。真实数据来源是探域 / OMS，现状是手工导入 CSV/TSV 或 JSON（页面上有导入入口），尚未做成定时同步。建议接手后确认：指标口径（采纳率 / 生成率 / 转化率 / 回复率 / 风控率 / 纯智占比）由谁负责统计、多久一次、从哪个系统导出。

P2 · 目标值与统计周期还没上云

「目标值」和「统计周期」这组配置目前存在各自浏览器的本地存储里，谁改了只影响自己，换台电脑就回到默认值。如果要求全组口径一致，需要把这块搬进云端 wb_kv。同理，表单未提交的草稿和深浅色主题也是本机偏好，不上云。

P2 · 旧密码表格的处置

桌面的《拼多多店铺信息【准确版】.xlsx》里仍是完整手机号和明文密码。工作台不再需要它，建议由原持有人确认后删除或转移到受控位置，别再散落在个人桌面。

P3 · 历史店铺与重复店名

128 家店铺中有 36 家是「历史」标记，另有 8 组名字极为相似的店铺——已确认每组确实是两家不同的店，不要合并。如果后续要清理历史店，请逐家确认后单独处理，不要批量删。

8.2 数据什么时候生效

改完约 0.3 秒写入云端；其他人需要刷新页面才看到（当前没有做实时推送）。如果你改完立刻刷新却看不到自己的改动，等 2 秒再刷。

8.3 不要做的事

  • 不要用旧链接录数据（见 P0）。
  • 不要在页面里批量删除店铺——工作台没有回收站，删了要从云端数据库恢复。
  • 不要把密码写进任何字段。系统已经不存密码，也没有地方存。

9. 排障手册

现象原因处理
页面弹出「数据加载失败」或「Could not find the table 'public.wb_records' in the schema cache」 连到了没有建表的云环境（换新应用后最容易发生） 让后台在对应应用里建 wb_records / wb_kv 并刷新 schema 缓存；确认产物指向的应用 ID 是否正确
控制台报 permission denied for table wb_records（码 42501） 未登录，或该表没给登录用户组授权 / 没建策略 先确认已登录；若是配置问题，检查表授权对象为 authenticated 且有团队策略
一直停在加载动画 会话过期或网络异常 刷新页面重新登录；仍不行看控制台是否有 401
登录后数据是空的 连到了另一个环境（新旧链接混用） 核对地址栏域名与 sharecode，用 P0 那条正式链接
同事看不到我改的内容 他没刷新，或他在旧链接上 让他刷新；核对链接
手机端侧栏打不开 窄屏下侧栏是抽屉模式 点左上角方形按钮唤出，点遮罩关闭

10.1 文件结构

路径作用

10.2 改代码 → 上线

  1. 只改 src/ 下的源文件，不要直接改 dist/index.html，下次构建会被覆盖。
  2. 构建：node src/build.cjs，产物同时写 signal-board.html 与 dist/index.html。
  3. 本地自测（不连真云）：WB_STUB=1 node src/build.cjs 生成带内存云桩的版本，配合本地静态服务打开。
  4. 发布：用 WorkBuddy 的站点发布能力，应用 ID 固定为 wbapp_6H4ne4Pivj47cmkaQcnAzt、域名前缀 ai-ops-workbench、入口 index.html。发布后链接不变。
构建脚本里有两道闸门（明文密码字面量、已下线的密码/保险箱代码）。构建失败先看报错，别注释掉闸门。

10.3 改代码时容易踩的坑

  • 产物是单文件，SDK 与配置都内联在 dist/index.html 里；换云环境必须改 src/build.cjs 里的 WB_CFG（endpoint + publishableKey），然后重新构建，否则页面还连旧环境。
  • 页面 ID 与 RENDER 映射在 src/app.js 的 PAGES 常量里；新增页面要同时补侧栏图标与渲染函数。
  • 账号表的「尾号」列在窄屏下保持显示，「使用人 / 岗位」两列会被隐藏，改列顺序时记得同步调整隐藏规则。
  • 改完务必确认构建产物里没有明文密码：直接搜 yongheng123 之类的字面量，命中即为事故。

12. 附：常用数据检查 SQL

在云数据库管理入口执行，用于核对交接后的数据是否完整。

目的语句
各集合条数select coll, count(*) from wb_records group by 1 order by 1;
账号是否还有残留字段select count(*) from wb_records where coll='accounts' and (data ? 'pwd' or data ? 'phone' or data ? 'hasPwd');
尾号是否合法select count(*) from wb_records where coll='accounts' and data->>'tail' ~ '^[0-9]{4}$';
KV 里有哪些键select k from wb_kv order by k;
策略与授权核对select tablename, policyname, roles::text from pg_policies where tablename in ('wb_records','wb_kv');
